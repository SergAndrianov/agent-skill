# ПлатиДом. Поиск и привязка начислений

[SCRUM-2163](https://javacode.atlassian.net/browse/SCRUM-2163) связывает через `relates to` две истории: [SCRUM-2164](https://javacode.atlassian.net/browse/SCRUM-2164) о поиске и [SCRUM-2165](https://javacode.atlassian.net/browse/SCRUM-2165) о сохранении и просмотре. Правила BR-01–BR-08 взяты из [бизнес-правил](../knowledge/Бизнес-правила.md), A-01–A-03 и A-13 — из [допущений](../knowledge/Допущения.md). Поставщик и источник начислений различаются по [глоссарию](../knowledge/Глоссарий.md).

## Граница и ответственность

На уровне контекста клиент использует ПлатиДом, а ПлатиДом запрашивает начисления у внешнего источника. ГИС ЖКХ представляет этот источник по учебному допущению A-01. Поставщик услуг определяет реквизиты и участвует в сценарии как предметная сущность. Фича заканчивается просмотром начислений по сохранённому счёту.

| Элемент | Ответственность и основание |
| --- | --- |
| Мобильное приложение банка | Принимает реквизиты и явное подтверждение. Показывает полученные значения, отсутствие данных, ошибки и время последнего успешного обновления. |
| Серверное приложение ПлатиДома | Получает идентификатор клиента из доверенной банковской сессии, проверяет владельца и правила ввода, запрашивает начисления, управляет подтверждением и обновлением снимка. Поиск и обновление выполняет одно серверное приложение по запросу клиента. |
| Хранилище ПлатиДома | Сохраняет привязки, признаки успешного поиска для подтверждения и последние успешные снимки. Привязка и снимок доступны при следующем входе, переживают перезапуск сервера и обновляются согласованно. |

## Проектные решения

- **Успешный поиск.** Сервер проверяет авторизацию, известность поставщика и формат непустого счёта до внешнего вызова. Предложение для учебной модели — таблица правил и справочник поставщиков на стороне сервера. Отсутствие полей в корректно полученной записи сохраняется как отсутствие значения. Только успешный ответ, явно означающий пустой результат, даёт состояние «Начисления не найдены». Тайм-аут и непригодный ответ дают ошибку с возможностью повтора.
- **Явное подтверждение.** После успешного поиска сервер сохраняет краткоживущую запись с непрозрачным идентификатором, владельцем, поставщиком, счётом, результатом и временем поиска. Подтверждение предъявляет этот идентификатор. Сервер проверяет владельца записи и берёт из неё исходные реквизиты. Для новой привязки по истёкшей записи требуется повторный поиск. Сбой источника не выдаёт идентификатор подтверждения. Пустой успех допустим по A-03.
- **Привязка и конкуренция.** При действительном подтверждении сервер атомарно создаёт привязку владельца с уникальностью по `(клиент, поставщик, лицевой счёт)`. Инициализация снимка результатом поиска входит в ту же транзакцию. При конфликте уникальности сервер возвращает существующую привязку и оставляет её снимок без записи. Вместе с операцией сервер фиксирует результат подтверждения. Повтор уже завершённой команды того же владельца по её идентификатору возвращает сохранённую привязку, даже если срок исходного поиска истёк.
- **Просмотр и обновление.** Список и действия по идентификатору привязки всегда ограничены владельцем из сессии. Сервер использует сохранённые реквизиты и при успешном обновлении сохраняет список и время вместе. Снимок включает полученные поля из A-13. При сбое сервер выдаёт доступный последний успешный снимок с признаком неактуальности и временем или возвращает ошибку, если снимка ещё нет. Пустой успешный снимок тоже имеет время. При перекрывающихся обновлениях более ранний результат не перезаписывает результат более нового успешного запроса.
- **Технологии и протоколы.** Android/iOS представляют нативные клиенты мобильного банка на одном логическом контейнерном виде. Java / Spring Boot предложен для HTTP API и интеграции. PostgreSQL и TLS предложены для долговечного хранения, уникальности и транзакций. Внутренний API предложен как HTTPS / JSON. HTTPS к ГИС ЖКХ — проектное допущение о транспорте. Формат сообщений и способ доступа предстоит сверить с контрактом.

Перед реализацией нужно подтвердить каталог и правила формата поставщиков, способ передачи и проверки банковской сессии, срок действия идентификатора поиска, транспорт и значения исходов внешнего API. Q-08 остаётся открытым для определения фактического контракта. В модели применены проверка формата из BR-02 и A-02 и объём A-03, где юридическое владение лицевым счётом находится за рамками истории.

## Покрытие критериев

| Критерий | Вход и действие | Сервер, источник и данные | Что видит клиент |
| --- | --- | --- | --- |
| 2164 / 1 · BR-02, BR-03 | Сессия, поставщик, валидный счёт, запуск поиска | Сервер после проверки запрашивает ГИС ЖКХ. Сохраняет запись успешного поиска с полученными полями. Без подтверждения привязки нет. | Сумма, валюта, срок и поставщик по ответу. Для пропущенного поля — «Нет данных». |
| 2164 / 2 · BR-02 | Пустой счёт или неверный формат | Сервер отклоняет ввод до обращения к ГИС ЖКХ, записи нет. | Ошибка валидации. |
| 2164 / 3 · BR-04, BR-05, A-03 | Валидный счёт, успешный пустой ответ | Сервер сохраняет признак успешного поиска. Действие сохранения остаётся за клиентом. | «Начисления не найдены». Можно явно подтвердить привязку валидного счёта. |
| 2164 / 4 · BR-04 | Источник недоступен или истёк тайм-аут | Сервер возвращает сбой поиска. Записи успешного поиска по этому запросу и привязки нет. | Ошибка источника и возможность повторить поиск. |
| 2164 / 5 · BR-01 | Поиск без сессии или поиск авторизованным клиентом по реквизитам с чужой привязкой | Без сессии сервер отклоняет запрос до вызова источника. При поиске с сессией он запрашивает источник и не включает в ответ привязки других клиентов. | Отказ в доступе или результат поиска соответственно. |
| 2165 / 1 · BR-05, A-03 | Явное подтверждение полного или пустого успеха | Сервер проверяет свою запись успешного поиска и сохраняет собственную привязку и начальный снимок транзакционно. Повторный вызов ГИС ЖКХ не нужен. | Подтверждение сохранения привязки. |
| 2165 / 2 · BR-06 | Повторное или параллельное подтверждение тех же реквизитов | Уникальность в БД разрешает одну запись. Сервер читает и возвращает существующую привязку. | Та же сохранённая привязка. |
| 2165 / 3 · BR-07 | Новый вход и выбор сохранённой привязки | Сервер читает привязки владельца. При обновлении отправляет сохранённые реквизиты в ГИС ЖКХ и записывает успешный снимок и время. | Собственная привязка в списке и запрос начислений без повторного ввода. |
| 2165 / 4 · BR-04, BR-08 | Сбой обновления с прежним снимком или без него | Сервер читает снимок и время владельца, сохраняет их без перезаписи при сбое. При отсутствии снимка возвращает только состояние ошибки. | Устаревшие данные с временем или ошибка без данных. |
| 2165 / 5 · BR-01 | Просмотр или изменение по идентификатору чужой привязки | Запрос к БД ограничен текущим владельцем. Сервер выдаёт общий отказ, запись и вызов ГИС ЖКХ отсутствуют. | Отказ без признака существования чужой привязки и без её данных. |
