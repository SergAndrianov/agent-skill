## Контекст и контейнеры

Авторизованный клиент настраивает автоплатёж и смотрит историю через мобильное приложение банка. ГИС ЖКХ по A-01 предоставляет начисления. Поставщик — организация, у которой ведётся лицевой счёт. Процессинг карт по A-12 принимает оплату и сообщает результат. Доступность источников и проверка средств показаны у процессинга как предполагаемая граница интеграции. Ответственный за эти проверки интерфейс предстоит подтвердить.

| Контейнер | Ответственность | Долговечные данные |
| --- | --- | --- |
| Мобильное приложение банка (`mobile`) | Запрашивает доступные источники, собирает настройки и согласие, показывает правило и результаты клиента. | Состояние правил и операций хранит БД через API. |
| API ПлатиДома (`api`) | Проверяет доступ и настройки, выполняет фоновую обработку, запрашивает начисления, передаёт оплату и сверяет исход. | Состояние продолжения и результаты записывает в БД. |
| База данных ПлатиДома (`db`) | Хранит состояние и обеспечивает атомарные ограничения для правил и попыток. | Привязки и снимки, версия правила и ссылка на согласие, ключ начисления и запроса, параметры отправки, внешний ID при наличии, состояние, исход и причины пропусков. |

В модели настройка, фоновый запуск и сверка выполняются одним приложением API. БД хранит данные для выбора незавершённых попыток после перезапуска. Механизм запуска обработки подключается по политике Q-01. Способ вычисления времени следующей сверки зависит от Q-03. Технологии и протоколы внутренних связей — проектное предложение, согласованное по составу с первой моделью.

## Как обрабатывается автоплатёж

1. **Настройка.** API берёт идентификатор клиента из проверенной банковской сессии и проверяет владение привязкой. Для активации или изменения проверяет, что выбранный источник доступен клиенту, лимит — положительная точная сумма в RUB, согласие относится к передаваемой конфигурации. Уникальность строки по `bindingId` и транзакция на запись дают одну активную версию. Версия содержит идентификатор источника, сумму лимита, валюту, состояние и ссылку на подтверждение. Схему доказательства и правила суммы с комиссией определяют Q-07 и Q-06.
2. **Проверка начисления.** При запуске API читает собственную привязку и правило, запрашивает сведения по реквизитам привязки. Для оплаты требуются известная идентичность начисления, подтверждённая актуальность, статус неоплаченного, валюта RUB, точная сумма `0 < сумма ≤ лимит` и достаточные средства по доступному источнику. Снимок для просмотра с признаком неактуальности не допускает оплату. Отсутствие надёжного ответа, нужных полей или правил проверки удерживает команду до получения определённого исхода. Сравнение выполняется в целых копейках без округления сверх лимита и конвертации валюты. Команда передаёт полную сумму начисления.
3. **Изменение до отправки.** Если API наблюдает новую сумму, валюту, состояние начисления или версию правила, предыдущая проверка теряет силу. В модели Q-02 остаётся открытым: продолжение возможно только после применения согласованной политики актуальности и изменения суммы, повторной проверки условий и средств. Например, новая сумма выше лимита гарантированно исключает оплату по BR-13, даже если прежняя сумма была допустима. Как подтверждается версия начисления на момент передачи, зависит от контракта источника и Q-02.
4. **Захват и единственная передача.** В качестве проектного решения API до сетевого вызова фиксирует в БД попытку, неизменяемый `paymentRequestId` и данные команды, включая канонический ID и реквизиты начисления, версию правила, сумму, валюту и ссылку на источник оплаты. Уникальный ключ попытки строится по канонической идентичности начисления в подтверждённой области источника (Q-05). Изменение суммы, версия правила и номер запуска не порождают новый ключ для того же начисления. Проверочные данные можно пересчитать до этой записи. Однократный переход к возможной отправке фиксирует параметры команды и допускает только одного исполнителя. При повторе, гонке или следующем запуске остальные читают существующую попытку и при необходимости уточняют её статус. Если повтор пришёл по другой привязке, защита от дубля остаётся общей для того же канонического начисления, а история и детали попытки остаются доступны только её владельцу. Здесь нужна проверка области уникальности и срока хранения защиты.
5. **Отключение и изменение при отправке.** Проектное решение сериализует окончательную проверку версии, начало передачи команды из API и запись новой настройки по одной привязке. Если отключение зафиксировано первым, команда блокируется. Если изменение зафиксировано первым, допуск проверяется по новой подтверждённой версии. Если команда уже передана транспортному клиенту, API фиксирует исход той же попытки, даже когда правило отключено. В реализации нужно проверить эту границу при нескольких экземплярах API и потере блокировки. При прерывании вокруг отправки, когда отсутствие сетевой передачи доказать нельзя, состояние уточняется по уже сохранённому ключу.
6. **Исход.** API связывает ответ с той же попыткой. Подтверждённый процессингом успех с суммой и ID операции сохраняется как «успешно». Явный окончательный отказ даёт «отклонено» и причину. После тайм-аута, в том числе до получения внешнего ID, API записывает «результат уточняется» и выполняет запрос состояния. Пока известен только `paymentRequestId`, запрос состояния использует его. После получения внешнего ID можно использовать ID операции по подтверждённому контракту. Повторный запуск и ответ «не найдено» при неизвестном исходе не открывают новую отправку. Сбой или превышение лимита, установленные до передачи, фиксируются как причины пропуска отдельно от отказа процессинга.
7. **Запоздалый ответ и выдача истории.** Поздний подтверждённый ответ по той же операции может завершить состояние «результат уточняется». Обновление результата проверяет идентичность операции и допустимость перехода. Старые промежуточные ответы не откатывают конечный исход. При противоречии подтверждённых исходов API передаёт случай на сверку по авторитетному источнику согласно Q-09 и не запускает новый платёж. Просмотр правил, результатов и причин пропуска ограничен владельцем проверенной сессии.

## Контракты и открытые решения

| Связь или политика | Что требуется подтвердить перед реализацией |
| --- | --- |
| API → ГИС ЖКХ | Семантика статуса «оплачено», валюта и сумма, канонический ID начисления и его область уникальности (Q-05), время или версия данных для Q-02. Источник по A-01 задан для учебного сценария. |
| API → Процессинг карт · команда | Подтверждение приёма ключа, область и срок дедупликации, параметры полной суммы и источника, правила окончательного успеха и отказа. API сверяет средства до отправки. Достаточность при списании и обработку изменения остатка между проверкой и командой должен обеспечивать согласованный контракт процессинга. |
| API → Процессинг карт · запросы | Система, которая подтверждает доступность источника и средства (Q-06), и запрос статуса по сохранённому ключу до получения внешнего ID. Q-03 и Q-09 определяют повторы опроса, качество ответа «не найдено», пределы сверки и обработку противоречий. |
| Политики API | Q-01 — момент запуска. Q-02 — актуальность и изменение суммы. Q-04 — допустимость новой попытки после окончательного отказа. Q-07 — способ подтверждения и доказательство согласия. |

Контракт процессинга пока не подтверждён. Возможность поиска по ключу до внешнего ID — условие реализации BR-17. A-09 задаёт требуемое поведение учебной интеграции. Если фактический интерфейс не умеет находить платёж по известному до отправки ключу, безопасное восстановление после потери первоначального ответа требует согласования другого контракта. По Q-02 основание для выбора политики пока отсутствует, поэтому критерии ниже проверяют ветви допуска условно.
