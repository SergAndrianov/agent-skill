## Граница и ответственность

Клиент работает через мобильное приложение банка. Поставщик — организация, у которой открыт лицевой счёт. Внешняя система, которую вызывает ПлатиДом, — ГИС ЖКХ по A-01. На диаграмме уровня 2 граница ПлатиДома охватывает три контейнера.

| Контейнер | Работа | Данные |
| --- | --- | --- |
| Мобильное приложение банка (`mobile`) | Показывает выбор поставщика, форму и исход поиска. Отправляет явное подтверждение, показывает свои привязки и обновляет начисления. | Держит параметры формы и ID поиска на текущем экране. Долговечное состояние привязок хранится на сервере. |
| API ПлатиДома (`api`) | Проверяет сессию, доступ и реквизиты. Вызывает источник, классифицирует результат, обрабатывает подтверждение, выдаёт список и обновляет начисления. | Использует правила формата и соответствия поставщиков из конфигурации. Данные клиента записывает через БД. |
| База данных ПлатиДома (`db`) | Хранит серверные результаты успешного поиска, собственные привязки и последние успешные снимки. Обеспечивает уникальность и атомарные записи. | Ключ клиента, идентификатор поставщика, лицевой счёт, результат поиска, привязка, поля снимка и время последнего успеха. |

Сценарии инициируются клиентом. API выполняет валидацию, интеграцию и сохранение в пользовательских запросах. Одна БД позволяет атомарно создать привязку и сохранить её начальный снимок.

## Проектные решения

- **Технологии.** iOS/Android, Java/Spring Boot, PostgreSQL, HTTPS/JSON и SQL/JDBC — предложенный стек. API получает стабильный идентификатор клиента из проверенного контекста банковской сессии. Формат сессии и способ её серверной проверки требуется подтвердить при интеграции с мобильным банком.
- **Проверка реквизитов.** API проверяет известного поставщика и непустой счёт по конфигурации этого поставщика. Нормализация допустима по правилам поставщика, например значимые начальные нули сохраняются. API останавливает запрос до ГИС ЖКХ при ошибке проверки. Перед реализацией нужно подтвердить источник правил, сопоставление идентификаторов поставщиков и допустимую нормализацию.
- **ГИС ЖКХ.** Контракт у стрелки `api → accrualSource` подлежит проверке. Нужны подтверждённые операция поиска, формат реквизитов, авторизация, доступность полей и способ различить пустой успешный ответ, неполные поля и сбой. Ответ с начислениями и пропущенным полем остаётся успешным при корректной структуре ответа. Поля сохраняются как отсутствующие и так же показываются. Неинтерпретируемый ответ относится к ошибке источника.
- **Явное подтверждение.** После успешного ручного поиска API сохраняет снимок вместе с серверным результатом `searchId → (clientId, providerId, account, snapshot, succeededAt)` и выдаёт непрозрачный ID. Успешный пустой ответ сохраняется как пустой снимок. Мобильное приложение показывает подтверждение для текущего результата и сбрасывает ID при изменении реквизитов или новом поиске. Команда передаёт только `searchId`. API проверяет владельца и допустимость результата и использует реквизиты из серверной записи. Срок подтверждения и хранения результатов нужно согласовать. После истечения срока для новой привязки нужен повторный поиск.
- **Одна привязка на комбинацию.** Уникальный ключ БД `(clientId, providerId, account)` и атомарная вставка с чтением существующей строки при конфликте дают один ID привязки при повторах и гонках. Начальный снимок сохраняется в той же транзакции. Повтор уже выполненной команды в пределах хранения доказательства возвращает текущую привязку и не откатывает снимок. Новый успешный поиск по тем же реквизитам позволяет подтвердить ту же комбинацию.
- **Обновление.** API извлекает реквизиты из привязки по `(clientId, bindingId)` и запрашивает источник. Снимок включает явно полученные поля A-13 и время успеха, поэтому пустой снимок отличим от отсутствия снимка. Успешные результаты для существующей привязки заменяют снимок условной записью по порядку запросов, чтобы запоздалый ответ на более ранний запрос не затёр более новый успешный снимок. Сбой возвращает статус ошибки и доступный снимок со временем успеха и признаком неактуальности. Q-02 оставляет открытым общий порог допустимого возраста начислений.
- **Доступ.** Список и каждое чтение или изменение привязки выполняются в области владельца из сессии. Чужой и неизвестный ID дают одинаковый ответ без данных. Поиск по реквизитам не выполняет чтение чужих привязок. Для этой фичи предусмотрены сохранение и обновление снимка, отвязка исключена по A-03.

## Покрытие критериев приёмки

Номер после решётки соответствует номеру критерия в карточке Jira. Для формата счёта границы задаются правилами конкретного поставщика (A-02).

| Критерий | Исходное состояние и событие | Ответственность и внешний вызов | Изменение данных и результат для клиента |
| --- | --- | --- | --- |
| SCRUM-2164 #1 · BR-01–BR-03, A-02, A-13 | Есть сессия, поставщик и корректный счёт. Клиент запускает поиск. Источник возвращает начисления с полным или частичным набором полей. | Мобильное приложение вызывает API. API проверяет доступ и формат, запрашивает ГИС ЖКХ. | БД сохраняет успешный результат и полученные поля. UI показывает сумму, валюту, срок и поставщика. Для каждого пропущенного поля показывает отсутствие значения. Привязка появится после подтверждения. |
| SCRUM-2164 #2 · BR-02 | Есть сессия. Клиент ищет с пустым счётом или счётом вне формата поставщика. | API возвращает ошибку валидации до вызова ГИС ЖКХ. | Записей поиска и привязки нет. UI показывает ошибку ввода. |
| SCRUM-2164 #3 · BR-04, BR-05, A-03 | Ввод корректен. ГИС ЖКХ отвечает успешно, список пуст. Клиент не подтверждает привязку. | API классифицирует ответ как пустой успех. | БД хранит ID успешного поиска и пустой снимок. UI показывает «Начисления не найдены». Привязка не создаётся. |
| SCRUM-2164 #4 · BR-04 | Корректный ввод. ГИС ЖКХ недоступна или ответ не позволяет установить исход. | API возвращает ошибку источника. Повтор поиска выполняет новый запрос источнику. | Нет нового ID успешного поиска или привязки. UI предлагает повторить поиск и показывает ошибку. |
| SCRUM-2164 #5 · BR-01 | Сессия отсутствует или просрочена. В соседнем случае сессия действительна и у другого клиента есть те же реквизиты. | API отклоняет запрос без сессии до ГИС ЖКХ. | SCRUM-2165 #1 · BR-05, A-03, A-13 | Поиск того же клиента успешно вернул начисления или пустой список. Клиент нажимает «Сохранить». | API проверяет серверный ID поиска, владельца и реквизиты из результата. Вызов ГИС ЖКХ при подтверждении не нужен. | БД атомарно сохраняет привязку в профиле клиента и начальный снимок, включая пустой. UI показывает подтверждение. |

Внешнего вызова нет. | Одна привязка, оба успешных ответа возвращают её ID. Повтор команды не перезаписывает более новый снимок. |
| SCRUM-2165 #3 · BR-07 | При следующем входе у клиента есть сохранённая привязка. Он открывает список и выбирает обновление. | API читает список владельца.
