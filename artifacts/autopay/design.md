## Граница и согласованность

Сохраняются названия контейнеров первой фичи: «Мобильное приложение банка», «Серверное приложение ПлатиДома», «Хранилище ПлатиДома». Их ответственность расширяется настройкой правил, исполнением и отслеживанием попыток. ГИС ЖКХ остается внешним источником по A-01; процессинг карт — внешней системой по A-12. Проверки не выделяются в отдельные контейнеры.

## Принятые учебные допущения
Пользователь подтвердил следующие решения 2026-11-15. Это учебные контракты, не подтвержденные возможности реальных внешних систем.
1. Запуск — событие получения начислений. Предложение реализации: сервер при сохранении полученных данных атомарно создает долговечную запись работы в PostgreSQL. Встроенный обработчик серверного приложения выполняет ее; отдельный брокер и отдельный сервис не требуются. Это внутреннее событие, а не утверждение о push API ГИС ЖКХ. Проверочный запрос перед оплатой не порождает рекурсивный запуск той же попытки.
2. Оплата картой банка, без комиссии. Банковская система предоставляет доступные клиенту карты и средства. Предварительная проверка остатка не гарантирует списание: окончательный успех устанавливается только процессингом.
3. Перед оплатой сервер повторно запрашивает начисление. Изменение суммы вызывает повтор всех проверок; при отсутствии достоверных данных оплата не отправляется.
4. Согласие дается при создании автоплатежа. Сохраняются клиент, время, версия условий и подтвержденная конфигурация. Изменения конфигурации также требуют подтверждения по BR-10.
5. После окончательного отказа автоматическая новая попытка не создается. Повторное событие возвращает состояние исходной попытки.
6. При неизвестном результате проверяется исходная операция через 1, 5, 15 минут от потери результата, затем ежечасно до суток. Далее состояние остается «результат уточняется», запись помечается для операционного разбора; нового платежа нет. Интерфейс операционного разбора вне этой фичи.
7. Запоздалый ответ сопоставляется по идентификатору исходной операции. Противоречивые результаты требуют запроса состояния у процессинга; до разрешения новый платеж запрещен. Достоверный успех не заменяется отказом из запоздалого сообщения.
8. Ключ начисления: источник + поставщик + идентификатор начисления, без клиента. Защитная запись не удаляется автоматически. Допущение контракта: идентификатор не переиспользуется для другого начисления в этой области. Без него автоматическая оплата блокируется. Повторы чужой привязки не раскрывают плательщика и его операцию.

## Архитектурные решения и данные
Сохраняются три контейнера первой фичи с расширенной ответственностью. Мобильное приложение показано как среда интерфейса ПлатиДома; прочие функции банка вне объема. Авторизованный клиент — предусловие; сервер всегда проверяет владельца привязки, правила и истории.

Предлагаются Kotlin/Swift для нативного интерфейса, Java/Spring Boot для серверных запросов и фоновой обработки, PostgreSQL для транзакций, уникальности и долговечных заданий. Это предложенный стек, не установленный факт. HTTPS/JSON для приложений и банковских контрактов, HTTPS для ГИС ЖКХ и PostgreSQL protocol/TLS для хранилища — архитектурные допущения; реальные контракты потребуют проверки перед реализацией. Связь человека с приложением использует UI, а не сетевой протокол. Стрелка указывает инициатора запроса; ответ включен в взаимодействие.

Данные: собственные привязки и снимки первой фичи; правило (привязка, ссылка на карту, лимит RUB, состояние, версия); подтвержденное согласие; глобальная защитная запись начисления; попытка (владелец, ключ начисления, снимок суммы, конфигурация, устойчивый ключ операции, состояние, причина, идентификатор процессинга); долговечное задание и время следующей проверки. PAN/CVV не хранятся: используются ссылки на платежный инструмент.

Предлагается уникальное ограничение на правило привязки и атомарный захват ключа начисления. Конкурентные обработчики используют одну сохраненную попытку. Ключ операции фиксируется до сетевого запроса и не меняется при восстановлении после сбоя. При сомнении, был ли запрос отправлен, выполняется проверка исходной операции по A-09, а не новая оплата. Неизвестный результат, успех и окончательный отказ сохраняют защитную запись.

Отключение/изменение правила и переход попытки к передаче в процессинг сериализуются сервером на одной версии правила. До передачи применяются новые настройки (A-11); после передачи отслеживается исходная операция. Сетевой тайм-аут не означает отказ или отмену. Состояния: «обрабатывается», «успешно», «отклонено», «результат уточняется»; пропуск сохраняется отдельно с причиной.

Критерии таблицы отражают проектное покрытие, не результаты тестирования реализации. Q-01—Q-07 и Q-09 разрешены в пределах принятого учебного сценария; Q-08 сохраняет прежнее уточнение формата счета. Для промышленной реализации требуется подтвердить внешние контракты, хранение защитных записей и порядок операционного разбора.
